# SPOILS — масштабирование: замеры, стресс-тест на VPS, размер сервера

Дата замера: 2026-10-04. Блок D/E. Скрипты: `scripts/load/`.

## 1. Коротко

- **Один мир (шард) на 24 игрока + ~60 NPC — это малая доля одного ядра.** На ноутбуке при 8 тестовых
  клиентах тик сервера занимал в среднем 0,95 мс из 50 мс бюджета (p95 1,8 мс), процесс — 5 % одного
  ядра, память 92 МБ (пик 108 МБ). Ни одного тика дольше 50 мс.
- **Экстраполяция на 24 + 60 NPC (это расчёт, а не замер):** тик в среднем 2–4 мс, p95 4–8 мс; CPU 20–50 %
  одного vCPU на VPS; память 150–250 МБ; трафик к игроку 1–8 КБ/с полезных данных (2,5–10 КБ/с с
  заголовками), от игрока ~1,9 КБ/с полезных (~4 КБ/с по сети). Средний тик — 4–8 % бюджета, запас по
  CPU ядра — в 2–5 раз.
- **Узкие места при запуске — не тик игры**, а: редкие выбросы тика 10–35 мс (сборка мусора или
  планировщик ОС; на «шумном» VPS их будет больше), нагрузка на Postgres в момент вайпа и расчётов, CPU
  у Next.js и исходящий трафик от загрузки спрайтов (~8 МБ на нового игрока).
- **Рекомендация для запуска:** один VPS на 4 vCPU (лучше с выделенными ядрами), 8 ГБ RAM, NVMe 80 ГБ,
  сеть 1 Гбит/с и от 2 ТБ трафика в месяц. На нём весь docker-compose: web, Postgres, game-server, cron.
  Подробно — раздел 8.
- Горячих мест в коде сервера замер не нашёл, поэтому код сервера не менялся.

|---|---|

| Сервер | настоящий `apps/game-server` из исходников (`node --import tsx`), порт 2669, `BATTLE_PERF_LOG=1`, запись реплеев включена |
| Web API | заглушка `scripts/load/web-stub.mjs`: отвечает на все HMAC-запросы сервера, как настоящий web для бесплатного кита (open / enter / exit / end / event / приём реплеев), проверяет подпись и считает запросы. Next.js и Postgres в этом замере не участвовали |
| Билеты | настоящие подписанные JoinTicket; секрет HMAC — случайный на каждый прогон, только в памяти (секрет из `.env` не использовался) |
| Часы мира | `WORLD_DEV_CLOCK_OFFSET_MS` ставит сервер на 1-ю минуту свежего цикла: вход открыт, вайп далеко |
| Клиенты | `scripts/load/clients.mjs`: colyseus.js с настоящей схемой `BattleState`, как браузер. Шлют ввод 30 раз/с: идут от зоны к зоне (60 % маршрутов — в центральную зону «Fuel Stop», чтобы встречаться), обходят стены, целятся в ближайшего видимого игрока или NPC и стреляют очередями, иногда делают перекат; PING каждые 2 с, перезарядка, лечение, обыск контейнеров (INTERACT → TAKE_ALL → SEARCH_CLOSE) примерно раз в 12 с, иногда граната. После смерти — новый вход. Это тестовые клиенты нагрузки, а не боты в игре: они занимают места людей, как браузер |
| Расписание | 0 клиентов 30 с → 1 клиент 60 с → 4 клиента 75 с → 8 клиентов 90 с (всего 4 мин 15 с). Первые 10 с каждой фазы в расчёт не входят |
| Что писали | каждый тик: время шага симуляции и всего тика (`server-probe.mts`); каждые 5 с: CPU и память процесса, паузы GC, задержка event loop, сколько NPC проснулось; `ps` каждые 5 с; у клиентов — байты каждого типа сообщений, RTT; у заглушки — запросы и байты |

Дополнительно — короткий прогон уже существующего бенча симуляции (`apps/game-server/src/sim/perf.bench.ts`)
на 24 человека + 60 NPC, 3 минуты игрового времени: он показывает цену боёв, которых в живом замере было мало.

### 3.5. Бенч симуляции: 24 человека + 60 NPC (без сети)

`perf.bench.ts 24 3 7 scripted max` — 3 минуты игрового времени заняли 3,1 с.

- шаг: среднее 0,38 мс, p99 1,09 мс, максимум 3,6 мс; мозги NPC — 23 % шага;
- проснувшихся NPC в среднем 38, максимум 48; 909 выстрелов, 187 попаданий, 11 убийств, 7 смертей людей.

Бенч крутит тики подряд на «горячем» процессоре, поэтому он быстрее живого сервера, где между тиками
50 мс простоя и сетевой ввод-вывод: при 8 клиентах живой шаг был 0,64 мс в среднем при меньшей нагрузке.
Для оценки живого сервера время из бенча умножаем на 2–3.

## 4. Как нагрузка растёт от 1 к 4 и 8 клиентам

- **Тик:** растёт примерно линейно, на ~0,05 мс в среднем и ~0,06 мс на p95 за каждого клиента
  (линейная подгонка: среднее = 0,55 + 0,050 × N мс). Сетевая часть — ~0,03 мс на клиента за тик.
- **CPU:** 1,4 % без игроков (34 спящих NPC, реплей), дальше ~0,4 % ядра на клиента
  (подгонка: 2,7 + 0,39 × N). Между 4 и 8 рост почти не виден: в фазе 4 клиентов была перестрелка
  с NPC, в фазе 8 клиенты больше шли — разброс сценария больше, чем вклад клиентов.
- **Память:** ~4 МБ RSS на клиента (StateView, буферы, сокет).
- **Трафик на клиента:** не зависит от числа клиентов (~0,9 КБ/с вниз), пока они не видят друг друга.
  Число клиентов меняет только сумму трафика.
- **Боёв было мало:** карта 28 672 × 28 672 px, скорость 260 px/с — дойти до центра ~1 мин. Событий `ev`
  — 0,3–0,5 в секунду на клиента, одна смерть за 4 минуты. Поэтому живой замер описывает фазу «бегаем и
  лутаем», а цену боёв берём из бенча симуляции (3.5) и оценок ниже.

## 5. Экстраполяция на 24 игрока + ~60 NPC

**Это расчёт по замерам выше, а не замер.** Проверить его должен стресс-тест на VPS (раздел 7).

| Величина | Замер, 8 клиентов | Оценка, 24 + 60 NPC | Откуда |
|---|---|---|---|
| Тик, среднее | 0,95 мс | 2–4 мс | шаг 1–1,5 мс (бенч 0,38 мс × 2–3 на живом сервере, больше NPC проснётся) + сеть 0,03 мс × 24 ≈ 0,8 мс, в толпе ×2 |
| Тик, p95 | 1,8 мс | 4–8 мс | тот же рост, хвост в боях длиннее |
| Тик, p99 / максимум | 3,3 / 33 мс | 10–20 / 30–50 мс | выбросы — GC и ОС; объектов в 3 раза больше — сборок больше |
| CPU процесса | 5,3 % ядра M3 | 12–25 % ядра M3 ≈ 20–50 % одного vCPU VPS | подгонка 2,7 + 0,39 × 24 ≈ 12 %, в боях ×1,5–2; ядро VPS медленнее M3 в 1,5–2 раза |
| Память (RSS) | 92 МБ (пик 108) | 150–250 МБ | +4 МБ на игрока, больше NPC, трупы, предметы на земле, буфер реплея. Полный 45-минутный цикл не мерили |
| Вниз на игрока, полезная нагрузка | 0,9 КБ/с | 1–8 КБ/с | каждый видимый движущийся игрок или NPC добавляет ~25 байт в патч за тик (≈0,5 КБ/с); выстрелы и звуки идут в `ev` |
| Вниз на игрока, по сети | ≈2,5 КБ/с | 2,5–10 КБ/с | +~70 байт заголовков WS/TCP/IP на сообщение, ~21 сообщение в секунду |
| Вверх от игрока | 1,85 КБ/с (≈4 КБ/с по сети) | столько же | 30 вводов в секунду не зависят от числа игроков |
| Исходящий трафик сервера | — | 0,5–2 Мбит/с; при круглосуточной полной загрузке 150–650 ГБ в месяц | 24 × (2,5…10) КБ/с |
| Реплей | 18 КБ/мин | 40–100 КБ/мин → 2–4,5 МБ за цикл → 60–150 МБ в сутки (32 цикла) → 1–2 ГБ в Postgres за 14 дней хранения | рост с числом событий и сущностей |

Итог: один шард помещается в одно ядро с запасом в 2–5 раз по CPU и больше чем в 10 раз по среднему
времени тика. При запуске упираться будем не в симуляцию.

## 6. Ограничения этого замера

- Ноутбук, а не VPS: другое ядро, свои фоновые процессы (load average 7–15); macOS, вероятно, уводит почти
  простаивающий процесс на энергоэффективные ядра (одна из причин, почему живой шаг медленнее бенча).
- Клиенты и сервер на одной машине: RTT нулевой, потерь пакетов нет, трафик посчитан как полезная
  нагрузка WebSocket, без заголовков.
- Без Next.js и Postgres: web заменён заглушкой, поэтому нагрузка на базу при входе, выходе и вайпе здесь
  не измерена.
- Всего 4 минуты и максимум 8 клиентов: утечки памяти за цикл, вайп, респаун NPC, работа chain-воркера
  не проверены.
- Мало боёв (см. раздел 4) — цена боёв взята из бенча симуляции.
- Сервер запускался через `tsx` из исходников, а в проде — `node dist/index.js`. После загрузки код тот же,
  разница только во времени старта.

## 7. План стресс-теста на VPS

### 7.1. Цель

Подтвердить, что один шард держит 24 человека три полных цикла подряд (45 мин × 3) с вайпами, респауном
NPC, записью реплеев и работающим chain-воркером на devnet, и найти первое узкое место: тик, GC, память,
сеть, Postgres или web.

### 7.2. Стенд

- **Сервер под тест:** VPS той конфигурации, которую берём в прод (раздел 8), с тем же
  `docker-compose.yml`: postgres, migrate, web, game-server, cron. Staging-домен, devnet,
  `REPLAY_RECORD` включён, cron с `/api/cron/chain-events` раз в минуту, `GUEST_PLAY_ENABLED=true`,
  `BATTLE_PERF_LOG=1`.
- **Game server с пробой:** на время теста запускаем его из исходников с пробой (тот же код, но с
  полными перцентилями тика и GC): `cd apps/game-server && node --import tsx ../../scripts/load/server-probe.mts`
  с переменными `LOAD_PROBE_DIR=/var/tmp/load/<прогон>` и обычными боевыми (`NODE_ENV=production`,
  `WEB_API_BASE_URL`, `GAME_SERVER_HMAC_SECRET`, `GAME_SERVER_ID`). Рядом
  `node scripts/load/ps-sample.mjs --pid <pid> --out /var/tmp/load/<прогон>/ps.csv`.
  Минимальный вариант без пробы — штатный `BATTLE_PERF_LOG=1` (раз в 30 с: среднее, p95 и max тика) и `pidstat`.
- **Генератор нагрузки:** отдельный VPS на 2 vCPU в том же регионе (8 клиентов съедают 1–2 % ядра, так что
  одна машина потянет и 24, и 100). Для замера RTT издалека — второй маленький VPS в другом регионе с
  2–4 клиентами.
- Часы на всех машинах синхронизированы (chrony/NTP): фазы клиентов сопоставляются с тиками сервера по времени.

### 7.3. Сценарии

| # | Сценарий | Расписание клиентов | Что проверяет |
|---|---|---|---|
| A | Разгон | 8 → 16 → 24, по 10 мин | кривая тик/CPU/память/трафик от числа игроков |
| B | Выносливость | 24 клиента на 3 полных цикла (≈2 ч 15 мин, начать за 5 мин до открытия цикла) | утечки памяти, вайпы, респаун NPC, реплеи, chain-воркер, Postgres во время вайпа |
| C | Наплыв | 24 клиента входят за 10 с сразу после открытия цикла | очередь входа: `/api/world/join`, `raids/enter`, спавн |
| D | Толпа | все 24 идут в одну зону (по умолчанию 60 % маршрутов и так ведут в центр) | худший случай для патчей, `ev` и зрения |
| E | Web недоступен 60 с | остановить контейнер web посреди цикла | сервер не падает, выходы досылаются, вход отвечает `web_unavailable` |
| F | Рестарт game server посреди цикла | `docker compose restart game-server` | void-orphans, новый шард, клиенты входят снова |

Клиенты в режиме `--tickets web` проходят весь путь игрока: гостевая сессия → `/api/world/join` → вход в
шард. После четырёх входов за цикл (лимит `WORLD.MAX_ENTRIES_PER_CYCLE`) клиент берёт нового гостя, после
вайпа ждёт открытия следующего цикла. Гости играют бесплатным китом. Чтобы нагрузить расчёты с настоящими
лоадаутами (склад, рынок, пул), нужны заранее созданные тестовые аккаунты с предметами — это следующий шаг
для скриптов (вход по cookie готовых аккаунтов).

### 7.4. Что мерить и чем

| Что | Чем |
|---|---|
| CPU на тик: p50/p95/p99/max тика и шага, тики > 50 мс, тиков в секунду | `server-probe.mts` → `ticks.csv`; `analyze.mjs` |
| Паузы GC (число, суммарно, максимум, major) | проба (`probe.jsonl`); при подозрениях `node --trace-gc` |
| Память за цикл: RSS, heap, external — тренд по циклам, значение после каждого вайпа | проба, `ps-sample.mjs`, `docker stats`; снимки кучи `--heapsnapshot-signal=SIGUSR2` в начале и в конце цикла |
| Профиль CPU при 24 игроках | `node --cpu-prof --cpu-prof-dir=/var/tmp/prof` на 60 с, открыть в Chrome DevTools |
| CPU хоста, steal time (соседи по VPS), диск | `vmstat 5`, `pidstat -u -r -p <pid> 5`, `iostat -x 5` |
| Трафик на клиента и всего | клиенты (`clients.jsonl`, по типам сообщений); интерфейс сервера: `sar -n DEV 5` или `ifstat`; `ss -tin` — RTT и ретрансмиты |
| RTT у игроков | PING/PONG у клиентов (p50/p95), отдельно из дальнего региона |
| Postgres во время вайпа и расчётов | `pg_stat_statements` (топ запросов по суммарному времени); снимки `pg_stat_activity` каждые 5 с (активные, idle in transaction, ожидающие); `pg_locks`; `log_min_duration_statement = 200` и `log_lock_waits = on`; `pg_stat_database` (транзакции, cache hit); размер таблиц до и после (реплеи) |
| Web API | access-лог nginx с `$request_time` по путям `/api/raids/*`, `/api/world/join`, `/api/admin/replays/ingest`; логи cron |
| Chain-воркер | длина очереди outbox и возраст самого старого события до и после вайпа; ошибки отправки |
| Ошибки | grep логов: `step failed`, `unhandled rejection`, `gave up`, `refused`, `[replay] … dropped` |

### 7.5. Скрипты

Всё в `scripts/load/` (Node ESM, без сборки):

| Файл | Что делает |
|---|---|
| `run.mjs` | локальный прогон целиком: заглушка web, game server с пробой, клиенты по расписанию, `ps`, отчёт. Ограничения для ноутбука: ≤ 300 с и ≤ 8 клиентов (снимаются флагами `--allow-long` / `--allow-many`) |
| `clients.mjs` | клиенты нагрузки; CLI для VPS: `--tickets web --web https://<staging> --server wss://<game> --schedule 8:600,16:600,24:8100 --out <dir>` |
| `server-probe.mts` | запуск game server с записью каждого тика, GC, event loop, CPU/памяти и числа NPC |
| `web-stub.mjs` | заглушка web API для теста game server отдельно от базы (`LOAD_HMAC_SECRET=… node scripts/load/web-stub.mjs --port 3999`) |
| `ps-sample.mjs` | `ps` раз в 5 с для одного pid |
| `analyze.mjs` | отчёт по каталогу прогона: `summary.md` и `summary.json` по фазам, линейные подгонки |
| `analyze.test.mjs` | тесты расчётов (`node --test scripts/load/analyze.test.mjs`) |

На VPS: после прогона скопировать `ticks.csv`, `probe.jsonl`, `ps.csv` с сервера в каталог клиентов
(там `clients.jsonl` и `phases.json`) и запустить `node scripts/load/analyze.mjs <каталог>`.

### 7.6. Пороги: прошёл / не прошёл (при 24 игроках)

| Метрика | Порог |
|---|---|
| Тик | p50 ≤ 3 мс, p95 ≤ 8 мс, p99 ≤ 20 мс, max ≤ 50 мс; тиков > 50 мс — не больше 1 за 10 минут; в каждом 30-секундном окне ≥ 19,5 тика в секунду |
| CPU game server | в среднем ≤ 40 % одного vCPU, в пиковом 5-секундном окне ≤ 70 %; steal time хоста < 5 % |
| GC | самая долгая пауза ≤ 15 мс; major GC не чаще раза в минуту; GC ≤ 2 % времени |
| Память | RSS ≤ 400 МБ; RSS в конце 4-го цикла не больше чем на 15 % выше, чем в конце 2-го (нет утечки); после вайпа heap возвращается в пределах 20 % от уровня после старта |
| Сеть | вниз ≤ 10 КБ/с на игрока в среднем (полезная нагрузка), вверх ≤ 3 КБ/с; RTT p95 в своём регионе ≤ 80 мс и не больше чем на 15 мс выше, чем на пустом сервере |
| Web / Postgres | `raids/enter` p95 ≤ 300 мс (игрок ждёт его при входе), `raids/exit` p95 ≤ 500 мс, вайп (`raids/end`) обработан ≤ 10 с; ноль ответов 5xx; CPU Postgres во время вайпа ≤ 70 %; соединений не больше пула (10 на процесс web), ожидание соединения ≤ 1 с; ноль дедлоков |
| Реплеи и chain | ни одного выброшенного куска реплея; очередь chain-событий разбирается за ≤ 5 мин после вайпа, ничего не застревает |
| Ошибки | ноль `step failed` и `unhandled rejection` в логах; все cron-задачи отвечают 2xx |

### 7.7. Отчёт

`summary.md` по каждому сценарию, график RSS и тика p95 по времени за 3 цикла, топ-10 запросов из
`pg_stat_statements`, профиль CPU и вывод: прошёл / не прошёл и что чинить первым.

## 8. Какой VPS брать

Game server однопоточный: для него важнее скорость одного ядра и стабильность (без «шумных соседей»),
чем число ядер. Один шард по оценке занимает 20–50 % одного vCPU.

| Вариант | Конфигурация | Для чего |
|---|---|---|
| Минимум (закрытый тест) | 2 vCPU, 4 ГБ RAM, 40 ГБ SSD | всё на одной машине, до ~24 игроков, без запаса на всплески |
| **Рекомендуется для запуска** | **4 vCPU (лучше выделенные ядра), 8 ГБ RAM, NVMe 80 ГБ, 1 Гбит/с, от 2 ТБ трафика в месяц** | web (Next.js) ~1 vCPU (оценка, не мерили), Postgres 1–2 ГБ RAM (`shared_buffers` ~1 ГБ), game server ≤ 0,5 vCPU, cron и chain-воркер; запас ×2 на вайп, деплой и пики лобби |
| Рост (2–4 шарда) | 8 vCPU, 16 ГБ, Postgres на отдельной машине или управляемый | после того как появятся несколько шардов (раздел 9) |

- Регион — рядом с основной аудиторией: RTT до 80 мс у большинства игроков важнее мощности.
- Тарифы с выделенными ядрами (dedicated vCPU): на общих vCPU соседи дают steal time и выбросы тика.
- Образы собирать в CI или на другой машине: `next build` на боевом VPS забирает все ядра и память.
- Диск: Postgres + реплеи (1–2 ГБ за 14 дней) + логи — 80 ГБ хватает с запасом.
- Трафик: игра — до 0,5–2 Мбит/с, но загрузка клиента (~6 МБ спрайтов + 2 МБ артов лобби на каждого
  нового игрока) быстро станет больше игрового трафика — см. CDN в разделе 9.

## 9. Будущие оптимизации

Выигрыш — оценка, кроме того, что прямо следует из замеров. По каждой — сначала стресс-тест на VPS, потом
решение.

| Оптимизация | Ожидаемый выигрыш | Цена | Когда |
|---|---|---|---|
| **Несколько шардов на процесс / процесс на ядро** (`WORLD.MAX_SHARDS` > 1, шард-переполнение) | шард ≈ 20–50 % vCPU → 2 шарда на процесс и процесс на ядро: 4 vCPU ≈ 6–8 шардов ≈ 150–200 игроков одновременно | 3–5 дней: директория с несколькими шардами, `/api/world/join` выбирает шард со свободными местами, пати-дропы в один шард. Несколько процессов — ещё 2–3 дня: Colyseus presence/driver на Redis или отдельный порт на процесс с маршрутизацией из web | когда первый шард начнёт заполняться (`world_full`) |
| **Регионы** (game server в Европе и США, общий web и база) | RTT для дальних игроков −60…−150 мс; вход дольше на ~100 мс (`raids/enter` через океан) | +1 VPS на регион; отдельные миры на регион; маршрутизация уже есть (`GAME_SERVER_URL_BY_COUNTRY`); 2–3 дня + эксплуатация | когда заметная доля игроков далеко от сервера |
| **Частота тика** (сейчас 20 Гц, ввод 30 Гц) | 15 Гц: −25 % CPU тика и −25 % трафика патчей, но хуже отзывчивость; 30 Гц: +50 % цены, ввод ждёт тик ≤ 33 мс вместо 50, интерполяция на 33 мс свежее | не одна константа: 05.10.2026 при 30 Гц упали 13 тестов симуляции — часы матча становятся дробными (33,3 мс), тайминги поиска, экстракции, звуков, гранат, окон и тревоги NPC сдвигаются на долю тика; нужен проход по симуляции (целые мс или тик 25 Гц = 40 мс) | после подачи, если задержка останется заметной |
| **Interest management дальше** (видимость и AOI уже есть) | дальние сущности обновлять 10 Гц, а не 20; позиции чужих игроков квантовать (float64 → int16 с шагом 1/8 px, свои координаты остаются точными для предсказания) → −40…−60 % байт патча в толпе | 3–5 дней; аккуратно с интерполяцией и StateView | если трафик вниз в боях > 10 КБ/с |
| **Бинарные дельты для `ev` и ввода** (схема уже шлёт бинарные дельты) | `ev`: компактный бинарный формат вместо msgpack (числовые id, квантованные углы) −50…−70 %; INPUT: mx/my/aim в int8/int16 — 60 → ~20 байт, вверх −65 % (с 1,85 до ~0,7 КБ/с) | 2–4 дня, новая версия протокола клиента и сервера | вместе с любой правкой протокола |
| **Реплей вне тика** (сжатие уже в пуле libuv) | запись и сериализация в worker_thread: −0,05…−0,1 мс на тик и нет всплеска при закрытии куска | 2–3 дня | если профиль покажет запись реплея в топе |
| **Пул соединений с базой** (сейчас `pg.Pool` max 10 на процесс web) | PgBouncer в transaction-режиме перед Postgres: нет исчерпания соединений при нескольких процессах web и всплеске на вайпе; пакетные вставки при вайпе | полдня настройки; проверить, что миграции и advisory-локи работают через PgBouncer | при втором процессе web или ожидании соединений в стресс-тесте |
| **CDN для спрайтов и артов** (`apps/web/public`: 5,9 МБ спрайтов + 2 МБ лобби) | весь статический трафик с VPS уходит в CDN: 8 МБ на нового игрока — это ~30–60 минут его игрового трафика; быстрее первая загрузка в дальних регионах | Cloudflare или аналог перед доменом с кэшированием `/sprites`, `/lobby`, `/_next/static`; ~0,5 дня, бесплатный тариф обычно достаточен | до публичного запуска |
| **Транспорт uWebSockets** (`@colyseus/uwebsockets-transport`) | меньше CPU на приём и отправку сообщений; сейчас вне тика (в основном сеть) уходит ~2/3 CPU процесса | 1 день + регрессия; другая обработка заголовков и закрытия соединений | если CPU game server станет заметен |
| **Запуск из сборки и флаги Node** | `node dist/index.js` (уже так в Docker); `--max-semi-space-size=16…32` — реже малые сборки GC | минуты | при настройке прод-окружения |

## 10. Как повторить локальный замер

```bash
# Прогон 0 → 1 → 4 → 8 клиентов (≈4,5 мин), результат и summary.md в каталоге --out
node scripts/load/run.mjs --out /tmp/spoils-load/run1 --schedule 0:30,1:60,4:75,8:90

# Пересчитать отчёт по готовому каталогу
node scripts/load/analyze.mjs /tmp/spoils-load/run1

# Тесты расчётов и проверка типов пробы
node --test scripts/load/analyze.test.mjs
apps/game-server/node_modules/.bin/tsc -p scripts/load/tsconfig.json

# Бенч симуляции 24 + 60 NPC, 3 минуты игрового времени (≈3 с)
cd apps/game-server && node_modules/.bin/tsx src/sim/perf.bench.ts 24 3 7 scripted max
```

`run.mjs` сам выбирает случайный HMAC-секрет (не печатает и не сохраняет), поднимает заглушку web, game server
на порту 2669 и убивает его по PID в конце. Если `packages/shared/dist` устарел — сначала
`pnpm --filter @extract/shared build`.
